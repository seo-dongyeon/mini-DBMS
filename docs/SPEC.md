# mini-DBMS 사양서

지금 코드가 실제로 하는 일을 적는다. Phase가 끝날 때마다 덧붙인다.

- 기준: Phase 3 (SQL 처리기 + B+ 트리 인덱스 + 스레드 풀 API 서버)
- 확인: 2026-11-16, 컨테이너(Ubuntu 24.04, g++ 13.3)
  - 단위 테스트 89개: AddressSanitizer 빌드와 ThreadSanitizer 빌드 둘 다 통과, TSan 경고 0개
  - 기능 테스트 1개 (sqlproc) 통과
  - 서버 기능 테스트 17개 (윈도우 파이썬 → 컨테이너 서버) 통과
  - 100만 건 벤치마크 (엔진, 서버) 실행

## 1. 범위

| 과제 요구 | 구현 |
|---|---|
| **Phase 1** 텍스트 파일의 SQL을 명령창으로 전달 | `sqlproc [--data 폴더] [--timing] 파일.sql` |
| SQL 파싱: INSERT, SELECT | 토큰화 → 문장 나누기 → 파싱 |
| INSERT: 파일에 저장 | 테이블 파일 끝에 한 줄 덧붙임 |
| SELECT: 파일에서 읽어 출력 | 조건에 맞는 줄 출력 |
| 테이블마다 파일로 관리 | `<테이블>.schema`, `<테이블>.db` |
| CREATE TABLE 없음 | 스키마 파일을 손으로 미리 만든다 |
| **Phase 2** 레코드에 ID 자동 부여 | INSERT마다 `다음 id`를 붙인다 |
| ID를 B+ 트리에 인덱스로 등록 | 메모리 B+ 트리에 `id → 줄 시작 바이트` 저장 |
| `WHERE id = ?`에 인덱스 사용 | 트리로 위치를 찾아 그 줄만 읽는다 |
| 100만 건 이상 INSERT 후 속도 비교 | `tests/benchmark/run_benchmark.sh` (14절) |
| Phase 1 처리기를 그대로 사용 | 토큰화·파싱은 손대지 않았다. 인덱스는 테이블 열기와 실행 단계에만 붙였다 |
| **Phase 3** 외부 클라이언트가 쓰는 API | HTTP 서버 `dbms_server`. `POST /query`에 SQL을 보내면 JSON으로 결과 (10절) |
| 스레드 풀로 요청을 병렬 처리 | 직접 만든 스레드 풀과 작업 대기열을 httplib에 끼웠다 (9절) |
| Phase 1·2를 내부 엔진으로 사용 | 서버와 sqlproc이 같은 `runSql()`과 `Database`를 쓴다 |
| 멀티 스레드 동시성 | 테이블마다 읽기-쓰기 락 (11절) |

아직 없는 것: DELETE·UPDATE·CREATE TABLE, 범위 검색, 인증.

## 2. 실행

### 명령창: sqlproc

```
sqlproc [--data 데이터폴더] [--timing] SQL파일
```

- `--data`: 스키마와 데이터 파일이 있는 폴더. 생략하면 현재 폴더 아래의 `data`.
- `--timing`: 문장마다 걸린 시간을 표준 에러로 출력한다. 테이블을 처음 열 때 인덱스를 만드는 시간은 따로 보여 준다.
- 결과는 표준 출력, 에러는 표준 에러로 나간다.

| 종료 코드 | 뜻 |
|---|---|
| 0 | 모든 문장 성공 (빈 파일 포함) |
| 1 | 실패한 문장이 하나 이상 있음 |
| 2 | 사용법이 틀렸거나 SQL 파일을 열 수 없음 |

### 서버: dbms_server

```
dbms_server [--data 폴더] [--host 주소] [--port 번호] [--threads 개수] [--queue 개수]
```

| 옵션 | 기본값 | 뜻 |
|---|---|---|
| `--data` | `data` | 스키마와 데이터 파일 폴더 |
| `--host` | `0.0.0.0` | 기다릴 주소. `0.0.0.0`이어야 컨테이너 밖(윈도우)에서 들어올 수 있다 |
| `--port` | `8080` | compose.yaml이 컨테이너 8080을 윈도우 8080에 연결해 둔다 |
| `--threads` | `8` | 스레드 풀의 일꾼 수 |
| `--queue` | `256` | 작업 대기열 크기 |

- Ctrl+C(SIGINT)나 SIGTERM을 받으면 새 연결을 그만 받고, 처리 중인 일을 끝낸 뒤 종료한다.
- 포트를 이미 쓰고 있으면 "서버를 열 수 없다"를 출력하고 종료 코드 1로 끝난다.

실행 예 (컨테이너 안):

```
./build/dbms_server --data /data/server
```

### 빌드와 테스트 (컨테이너 안에서)

```
cmake -S . -B build -G Ninja
cmake --build build
ctest --test-dir build --output-on-failure
```

- 기본 빌드는 AddressSanitizer(메모리 실수 검사)가 켜져 있다. 속도를 잴 때는 `-DDBMS_SANITIZE=OFF`.
- ThreadSanitizer(스레드끼리 락 없이 같은 데이터를 만지는지 검사):

```
cmake -S . -B build/tsan -G Ninja -DDBMS_SANITIZE=OFF -DDBMS_TSAN=ON
cmake --build build/tsan --target unit_tests
setarch $(uname -m) -R ./build/tsan/unit_tests
```

`setarch`는 WSL2에서 TSan 실행 파일이 무작위로 죽는 문제를 피하는 방법이다 (팀 환경 메모).

- 엔진 벤치마크: `bash tests/benchmark/run_benchmark.sh [건수]`
- 서버 테스트 (서버를 켠 뒤 윈도우에서):

```
python tests/server/test_server.py
python tests/server/bench_server.py
```

파이썬은 표준 라이브러리만 쓴다. 다른 주소면 환경 변수 `DBMS_URL`로 바꾼다.

## 3. 처리 흐름

```
SQL 글자 (파일 내용 또는 HTTP 본문)
   ↓                                              sql_runner.cpp  runSql()
맨 앞의 UTF-8 BOM 떼기                              ← sqlproc과 서버가 같이 쓴다
   ↓
토큰화: 전체를 토큰으로 쪼갠다                       tokenizer.cpp   tokenize()
   ↓
문장 나누기: ';' 토큰마다 자른다                     tokenizer.cpp   splitStatements()
   ↓
문장마다 ─ 파싱: 토큰을 Statement 구조로             parser.cpp      parseStatement()
          └ 실행                                    executor.cpp    executeStatement()
               ├ 테이블 열기 (처음 한 번)            database.cpp    openTable()
               │    스키마 읽기 → 데이터 파일을 읽어 B+ 트리와 다음 id 만들기
               ├ INSERT: 쓰기 열쇠 → 파일 끝에 쓰기 → 트리에 넣기
               └ SELECT: 읽기 열쇠 → WHERE id면 트리로 한 줄, 아니면 파일 전체
   ↓
결과: sqlproc은 글자로 출력 (formatResult), 서버는 JSON으로 응답 (buildQueryJson)
```

토큰화를 문장 나누기보다 먼저 한다. 글자 값 안의 `;`(`'안녕; 반가워'`)에서 문장이 잘리지 않게 하려는 것이다.

## 4. SQL 문법

```
INSERT INTO 테이블 VALUES ( 값 , 값 , ... ) ;
SELECT * FROM 테이블 [ WHERE 컬럼 = 값 ] ;
SELECT 컬럼 , 컬럼 , ... FROM 테이블 [ WHERE 컬럼 = 값 ] ;
```

| 요소 | 규칙 |
|---|---|
| 키워드 | `INSERT INTO VALUES SELECT FROM WHERE`. 대소문자를 구분하지 않는다 |
| 테이블·컬럼 이름 | 영문자나 `_`로 시작하고 영문자, 숫자, `_`로 이어진다. **대소문자를 구분한다** |
| 숫자 값 | 정수만. 앞에 `-`를 붙일 수 있다. 64비트 범위를 넘으면 에러 |
| 글자 값 | 작은따옴표로 감싼다. 안에 따옴표를 쓰려면 두 번 쓴다 (`'it''s'`). 줄바꿈, 쉼표, `;`를 그대로 넣을 수 있다 |
| 주석 | `--`부터 그 줄 끝까지 |
| 공백 | 토큰 사이의 띄어쓰기, 탭, 줄바꿈은 개수와 상관없다. `id=1`과 `id = 1`은 같다 |
| 문장 끝 | 모든 문장은 `;`로 끝나야 한다. 내용 없는 `;`는 무시한다 |

INSERT의 값은 **id를 뺀** 나머지 컬럼을 스키마 순서대로 적는다. SELECT의 컬럼 목록은 적은 순서대로 출력되고 같은 컬럼을 두 번 적어도 된다. WHERE는 `=` 조건 하나만 받는다.

## 5. 파일 형식

### 스키마: `<데이터폴더>/<테이블>.schema`

```
id INT
name TEXT
age INT
```

- 한 줄에 `컬럼이름 타입`. 타입은 `INT`(64비트 정수)와 `TEXT`뿐이고 대소문자는 상관없다.
- 첫 컬럼은 반드시 `id INT`다. 그 밖에 컬럼이 하나 이상 있어야 한다.
- 빈 줄과 윈도우 줄바꿈은 허용한다.
- **이 파일이 있으면 테이블이 있는 것이다.** 없으면 "테이블이 없다" 에러가 난다.

### 데이터: `<데이터폴더>/<테이블>.db`

```
1,민수,30
2,서울\,강남,25
```

- 레코드 하나가 한 줄이고 칸은 쉼표로 나눈다. 칸 순서는 스키마 순서다.
- 값 안의 특수 글자는 역슬래시를 붙여 저장한다.

| 값 안의 글자 | 저장되는 모양 |
|---|---|
| `\` | `\\` |
| `,` | `\,` |
| 줄바꿈 (LF) | `\n` |
| 캐리지 리턴 (CR) | `\r` |

- 그래서 파일 안의 진짜 줄바꿈은 항상 레코드의 끝이다. B+ 트리가 "줄 시작 바이트"만 알면 그 레코드를 읽을 수 있는 이유다.
- 줄마다 길이가 달라서 `id`만으로 파일 위치를 계산할 수 없다. 그래서 인덱스가 필요하다.
- 파일이 아직 없으면 빈 테이블로 본다. 첫 INSERT 때 만들어진다.
- 읽을 때 빈 줄과 줄 끝의 윈도우 줄바꿈은 건너뛴다.
- 파일이 줄바꿈 없이 끝나 있으면(손으로 고친 경우), 다음 INSERT는 줄바꿈을 먼저 넣고 쓴다.

### 어디에 저장되나

| 쓰임 | 폴더 | 윈도우에서 보이나 |
|---|---|---|
| sqlproc 기본값 | 레포의 `data/` (= 컨테이너 `/work/data`) | 보인다. `data/*.db`는 git에서 뺐다 |
| 엔진 벤치마크 | `/data/bench` (Docker 볼륨) | 안 보인다. 컨테이너 안에서만 |
| 서버 테스트 | `/data/server` (Docker 볼륨, 실행 예) | 안 보인다 |
| 단위·기능 테스트 | `/tmp/...` 임시 폴더 | 테스트가 끝나면 지운다 |

B+ 트리는 파일로 남지 않는다. 메모리에만 있다가 프로그램이 끝나면 사라지고, 다음에 켤 때 `.db`를 읽어 다시 만든다.

## 6. id

- id는 프로그램이 붙인다. 1부터 시작해 INSERT마다 1씩 커진다.
- 다음 id는 메모리에 있다. 테이블을 처음 열 때 데이터 파일을 읽어 `가장 큰 id + 1`로 정한다. 줄 순서와 상관없다.
- INSERT에 id를 적으면 값의 개수가 맞지 않아 에러가 난다.
- 실패한 INSERT는 id를 쓰지 않는다.
- 데이터 파일에 같은 id가 두 번 있으면 테이블을 열 때 에러가 난다.
- 서버에서 여러 INSERT가 동시에 와도 id가 겹치지 않는다 (11절).

## 7. B+ 트리 인덱스

`src/bplus_tree.*`. 메모리 기반이고, STL 그릇 없이 고정 크기 배열과 포인터로 만들었다.

### 구조

```
이정표 노드: 키 + 자식 포인터 (자식은 키보다 하나 많다)
잎 노드:     키 + 값(줄 시작 바이트) + 오른쪽 옆 잎 포인터
```

- 노드 하나에 키를 최대 128개 담는다(`BPLUS_MAX_KEYS`). 테스트에서는 3, 4로 줄여 쪼개기를 확인한다.
- 키는 id, 값은 데이터 파일에서 그 레코드 줄이 시작하는 바이트 번호다. 레코드 자체는 트리에 없다.
- 이정표의 키 `[5 | 9]`는 "5 미만은 0번, 5 이상 9 미만은 1번, 9 이상은 2번 자식"이라는 뜻이다.

### 찾기

뿌리에서 잎까지 층마다 노드 안에서 **이진 탐색**으로 자식 하나를 골라 내려간다. 잎에서 다시 이진 탐색으로 키를 찾는다.

### 넣기

1. 찾기처럼 내려가 들어갈 잎을 정한다. 이미 있는 키면 넣지 않는다.
2. 잎 안에서 이진 탐색으로 자리를 찾고, 뒤쪽 키와 값을 함께 한 칸씩 밀고 넣는다.
3. 키가 한도를 넘으면 쪼갠다.
   - **잎**: 반으로 나누고 오른쪽 첫 키를 부모에 **복사**한다. 잎에는 모든 키가 남아야 한다.
   - **이정표**: 가운데 키를 부모로 **이동**한다. 양쪽에는 남지 않는다.
   - **뿌리**: 쪼개지면 그 위에 새 뿌리를 만든다. 트리는 위로만 자라서 모든 잎의 깊이가 같다.

### 쓰는 곳

| 때 | 하는 일 |
|---|---|
| 테이블을 처음 열 때 | 데이터 파일을 처음부터 읽으며 줄마다 `(id, 줄 시작 바이트)`를 넣는다 |
| INSERT | 파일 끝에 먼저 쓰고, 성공하면 `(id, 쓴 위치)`를 넣는다. 그다음 다음 id를 올린다 |
| `SELECT ... WHERE id = 값` | 트리에서 위치를 찾아 그 바이트로 이동해 한 줄만 읽는다. 없으면 0줄 |
| 그 밖의 SELECT | 트리를 쓰지 않고 파일 전체를 읽는다 (선형 탐색) |

INSERT에서 파일을 먼저 쓰는 이유: 반대로 하면 쓰기가 실패했을 때 트리가 없는 줄을 가리킨다. 트리로 읽은 줄의 id가 찾던 id와 다르면(파일을 밖에서 고친 경우) 에러를 낸다.

삭제(합치기)는 과제 범위가 아니라서 없다. 잎끼리 연결은 있지만 범위 검색은 아직 쓰지 않는다.

## 8. sqlproc 출력

INSERT:

```
INSERT OK (id=1)
```

SELECT: 첫 줄에 컬럼 이름, 그 아래 한 줄씩, 마지막에 줄 수.

```
id | name | age
1 | 민수 | 30
(1 rows)
```

`--timing`을 주면 표준 에러에 이렇게 나온다.

```
[timing] 1번째 줄: users 테이블 열기 + 인덱스 만들기 288.925 ms (1000000건)
[timing] 1번째 줄: SELECT (B+ 트리) 0.074 ms, 결과 1줄
[timing] 5번째 줄: SELECT (선형 탐색) 226.300 ms, 결과 1줄
```

## 9. 서버 구조

```
윈도우 클라이언트 (파이썬 등)
   │  HTTP 요청 → localhost:8080
   │  Docker Desktop이 컨테이너 8080으로 넘겨 줌
   ▼
dbms_server (컨테이너 안)
 ┌──────────────────────────────────────────────────────────────┐
 │ httplib: 연결을 받는 스레드 1개                                │
 │    │ 연결이 들어올 때마다 enqueue(그 연결을 처리하는 일)          │
 │    ▼                                                          │
 │ ThreadPoolTaskQueue  ← httplib의 스레드 풀 자리에 끼운 연결부     │
 │    ▼                                                          │
 │ JobQueue (작업 대기열, 직접 만든 연결 리스트, 최대 256칸)          │
 │    │ 꽉 차면 연결 받는 스레드가 자리가 날 때까지 기다린다           │
 │    ▼                                                          │
 │ 일꾼 스레드 8개 (ThreadPool)                                   │
 │    │ 하나 꺼내서: HTTP 읽기(httplib) → 경로 찾기 → /query 핸들러  │
 │    ▼                                                          │
 │ runSql() → executeStatement() → Database / Table (락)          │
 │    ▼                                                          │
 │ buildQueryJson() → HTTP 응답                                   │
 └──────────────────────────────────────────────────────────────┘
```

| 부분 | 파일 | 누가 만들었나 |
|---|---|---|
| 소켓, HTTP 읽기·쓰기, 경로 찾기 | httplib (cpp-httplib 0.14.3) | 라이브러리 |
| 연결 처리 일을 받는 연결부 | `server_main.cpp` `ThreadPoolTaskQueue` | 직접 |
| 작업 대기열 | `thread_pool.cpp` `JobQueue` | 직접. STL 그릇 없이 연결 리스트 |
| 일꾼 스레드 | `thread_pool.cpp` `ThreadPool` | 직접 |
| 경로와 JSON | `http_api.cpp` | 직접 |
| SQL 엔진 | Phase 1·2 코드 | 직접 |

httplib는 원래 자기 스레드 풀을 갖고 있다. `server.new_task_queue`에 우리 것을 넣어 그 자리를 바꿨다. 그래서 과제의 "스레드 풀을 구성"하는 부분은 우리 코드다.

### 작업 대기열과 스레드 풀

- 대기열은 머리(`head_`)에서 꺼내고 꼬리(`tail_`)에 넣는 단일 연결 리스트다.
- 모든 넣기·꺼내기는 mutex 하나로 묶는다.
- 비어 있으면 일꾼은 `notEmpty_`에서 잠들고, 일이 들어오면 하나가 깨어난다.
- 꽉 차 있으면 넣는 쪽이 `notFull_`에서 잠들고, 일꾼이 하나 꺼내면 깨어난다. httplib 0.14.3의 `enqueue()`는 결과를 돌려주지 않아 "거절"을 할 수 없어서 이렇게 했다. 요청이 몰려도 메모리가 끝없이 늘지 않는다.
- 일꾼은 꺼낸 일을 실행하고 다시 꺼내러 간다. 일에서 예외가 나도 일꾼은 죽지 않는다.
- 끌 때는 대기열을 닫는다. 이미 들어온 일은 다 처리하고, 일꾼을 모두 `join`한다.

## 10. HTTP API

### `GET /health`

서버가 살아 있는지 확인한다. 항상 `200 {"ok":true}`.

### `POST /query`

본문 전체가 SQL이다. 문장을 여러 개 보내도 된다. 결과는 문장 순서대로 `results`에 담긴다.

요청:

```
POST /query
Content-Type: text/plain; charset=utf-8

INSERT INTO users VALUES ('민수', 30);
SELECT * FROM users WHERE id = 1;
SELECT * FROM nothing;
```

응답 (실패한 문장이 있어서 400):

```json
{"ok":false,"results":[
  {"line":1,"ok":true,"type":"insert","id":1},
  {"line":2,"ok":true,"type":"select","columns":["id","name","age"],
   "rows":[[1,"민수",30]],"rowCount":1,"usedIndex":true},
  {"line":3,"ok":false,"error":"테이블이 없다: nothing (...)"}
]}
```

| 칸 | 뜻 |
|---|---|
| `ok` (맨 바깥) | 모든 문장이 성공했나 |
| `line` | 그 문장이 시작한 줄 |
| `type` | `insert` 또는 `select` |
| `id` | INSERT가 붙인 id |
| `columns`, `rows` | SELECT 결과. INT 컬럼은 JSON 숫자, TEXT는 문자열 |
| `usedIndex` | B+ 트리로 찾았으면 true, 파일 전체를 읽었으면 false |
| `error` | 실패한 이유. 메시지는 sqlproc과 같다 (13절) |

### 상태 코드

| 코드 | 언제 |
|---|---|
| 200 | 모든 문장 성공 |
| 400 | 실패한 문장이 하나라도 있음 (본문에 문장별 결과), 또는 실행할 문장이 없음 (빈 본문, 주석만, `;;`) |
| 404 | 없는 경로나 방법 (`GET /query` 포함). 본문 `{"ok":false,"error":"지원하지 않는 요청이다: ..."}` |
| 413 | 본문이 8MB(`MAX_QUERY_BYTES`)를 넘음. httplib가 본문을 읽지 않고 거절하고, 핸들러는 불리지 않는다. 본문 `{"ok":false,"error":"본문이 너무 크다 (8MB까지)"}` |

- 문장 하나가 실패해도 다음 문장은 실행한다. sqlproc과 같다.
- 한 요청 안의 문장들은 한 일꾼이 차례로 실행한다. 다른 요청의 문장이 사이에 끼어들 수는 있다 (트랜잭션 없음).

## 11. 동시성

### 무엇을 잠그나

| 공유하는 것 | 위험 | 막는 법 |
|---|---|---|
| 작업 대기열 | 두 일꾼이 같은 일을 꺼냄 | `JobQueue`의 mutex |
| 테이블 목록 (`Database`) | 두 요청이 같은 테이블을 동시에 처음 열어 인덱스를 두 번 만듦 | `tablesMutex_`. 목록을 보고 고치는 동안 잠근다 |
| `nextId` | 두 INSERT가 같은 id를 받음 | 테이블 쓰기 열쇠 |
| 데이터 파일 끝 | 두 INSERT의 줄이 섞여 쓰임 | 테이블 쓰기 열쇠 |
| B+ 트리 | INSERT가 쪼개는 도중에 SELECT가 내려감 | 쓰기 열쇠 / 읽기 열쇠 |
| 파일 읽는 위치 | 두 SELECT가 한 파일 핸들의 위치를 서로 옮김 | 핸들을 같이 쓰지 않는다. SELECT마다 파일을 따로 연다 |

### 테이블마다 읽기-쓰기 락 (`std::shared_mutex`)

```
SELECT ████          ← 읽기 열쇠: 여럿이 같이 들어간다
SELECT ████
INSERT     ████      ← 쓰기 열쇠: 혼자. 읽는 사람이 다 나가야 받는다
SELECT         ████
```

INSERT는 쓰기 열쇠를 쥔 채로 네 가지를 한 묶음으로 한다.

```
1. id = nextId
2. 데이터 파일 끝에 쓰기
3. B+ 트리에 (id, 위치) 넣기
4. nextId + 1
```

중간에 다른 INSERT가 끼면 같은 id를 받고, SELECT가 끼면 트리는 있는데 파일에는 없는 줄을 볼 수 있다. 쓰기 열쇠를 쥐고 있으면 아무도 못 들어온다.

값 개수와 타입 확인은 스키마만 보므로 열쇠를 잡기 전에 한다. 스키마는 테이블을 연 뒤 바뀌지 않는다.

### 검증

- 단위 테스트: 스레드 8개가 INSERT 1,600건을 동시에 넣으면 id가 1~1600으로 겹치지 않고, 파일이 정확히 1,600줄이고, id마다 자기가 넣은 줄을 찾는다. 쓰는 스레드 2개와 읽는 스레드 4개를 같이 돌려도 반쯤 쓰인 줄을 보지 않는다. 테이블을 8개 스레드가 동시에 열어도 인덱스는 한 번만 만든다.
- ThreadSanitizer 빌드로 단위 테스트 89개를 돌려 경고 0개.
- 서버 테스트: 클라이언트 32개가 INSERT 800건을 동시에 보내면 id가 겹치지 않고 빈틈없이 이어진다. 읽기·쓰기 300건을 동시에 보내도 모두 성공한다.

## 12. 에러 처리 (엔진)

에러는 sqlproc에서 `ERROR (N번째 줄): 내용`, 서버에서 `{"line":N,"ok":false,"error":"내용"}`으로 나온다.

**문장 하나가 실패해도 다음 문장은 실행한다.** 예외는 토큰화 에러다. 따옴표가 안 닫히면 어디까지가 문장인지 알 수 없으므로, 그 앞의 완성된 문장까지만 실행하고 에러를 낸다.

## 17. 알려진 한계

- **연결 하나가 일꾼 하나를 차지한다.** 클라이언트가 연결을 유지(keep-alive)하면 그동안 일꾼이 묶인다. 일꾼이 8명이니 연결을 붙잡은 클라이언트 8개가 있으면 다른 요청은 기다린다.
- **실행할 때마다(sqlproc) 인덱스를 다시 만든다.** 서버는 테이블을 처음 열 때 한 번. 인덱스를 만드는 동안 다른 테이블 열기도 기다린다.
- **id 말고 다른 컬럼은 인덱스가 없다.** 항상 선형 탐색이다.
- **순서대로 넣으면 잎이 반만 찬다.** 100만 건이면 트리가 50MB쯤 쓴다 (코드의 `shortcut:` 주석).
- **SQL 전체를 한 번에 토큰화하고, 결과를 전부 메모리에 모은 뒤 내보낸다.** 큰 SQL이나 큰 결과는 메모리를 많이 쓴다.
- 트랜잭션이 없다. 한 요청의 문장들 사이에 다른 요청이 끼어들 수 있다.
- 서버와 sqlproc이 같은 데이터 폴더를 동시에 쓰면 id가 겹치고 인덱스가 어긋난다. 락은 한 프로그램 안에서만 통한다.
- 인증이 없다. 포트에 접속할 수 있으면 누구나 쓸 수 있다.
- 값이 올바른 UTF-8이 아니면 JSON 응답도 올바른 UTF-8이 아니다.
- 쓰고 나서 버퍼를 비우기(flush)까지만 한다. 전원이 꺼지는 상황에서 디스크에 남는다는 보장은 없다.
- WHERE는 `=` 하나뿐이다. 테이블·컬럼 이름에 한글을 쓸 수 없다.
